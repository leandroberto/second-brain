# Módulos: plano de implementação

> **Para agentes:** sub-skill obrigatória: use superpowers:subagent-driven-development (recomendado) ou superpowers:executing-plans para implementar este plano tarefa por tarefa. Os passos usam checkbox (`- [ ]`) para acompanhamento.

**Objetivo:** o second-brain passa a carregar módulos de outros repositórios (aba na UI, rotas, tarefas agendadas, estado,
MCP, IA e avisos) sem que nenhum código deles entre aqui.

**Arquitetura:**
- Novo pacote `@brain/module-sdk` (só tipos + `defineModule`).
- No core, a pasta `packages/core/src/modules/` concentra carregador, contexto restrito, estado, agendador e avisos.
- A API monta as rotas, a aba (iframe com origem opaca e token de página) e as notificações.
- O MCP registra as ferramentas e as executa no `serve`. A UI e o desktop são clientes HTTP.

**Stack:** TypeScript estrito, Node ≥ 22.5, pnpm workspaces, zod 4, vitest, React/Vite (UI), Electron (desktop).

**Spec:** `docs/superpowers/specs/2026-11-11-modulos-design.md`. Leia junto: os §§ citados nas tarefas estão lá.

**Base:** `main` com a base do vault sincronizado já aplicada (estado externo, política `additive`, motor de assistente, desktop).

## Restrições globais

- Repositório **público**: nenhum módulo privado, empresa, sistema, host ou pessoa em código, testes, fixtures ou docs. O único módulo citado é o exemplo `lembrete`.
- O SB nunca importa um módulo pelo nome; só pela lista `modules` da config do vault.
- Sem módulos configurados, o comportamento atual não muda, e toda a suíte (`pnpm test`, `pnpm typecheck`, `pnpm lint`) continua passando.
- Toda escrita de conhecimento de módulo passa pela fachada `Brain` com `principal("agent", "module/<id>", "module")`. Módulo nunca é humano.
- `id` de módulo: `/^[a-z][a-z0-9-]{1,30}$/`. Ferramenta MCP: `<id>_<nome>`. Rotas: `/api/modules/<id>/...`. Estático: `/modules/<id>/...`.
- O estado de módulos fica **sempre** fora da pasta do vault: `<stateDir>/modules/` com `state.external`; senão `~/.local/state/second-brain/<stateSlug(vault_name)>/modules/`.
- O SB nunca usa `instanceof` em schemas de módulo: só a interface Standard Schema (`~standard.validate`). O módulo usa zod 4.
- O Claude roda pela assinatura (o login do `claude` da máquina). "api-token" é sempre o token **local** do SB.
- Mensagens ao usuário em português.

## Foco de revisão

1. **Módulo que lança no `import()` ou no `iniciar()`:** o `serve` sobe assim mesmo, o módulo aparece `falho` com a causa e os outros funcionam. *Teste: Tarefa 2, `iniciar que lança deixa o módulo falho e os demais ativos`.*
2. **Agente local com o api-token tenta acionar uma rota de ação externa:** recebe 403 antes do handler. *Teste: Tarefa 6, `api-token só acessa _mcp e GET /api/modules`, e `rota humano:true recusa api-token`.*
3. **PC desligado no horário e ligado depois, duas vezes no mesmo dia:** roda uma vez só, e não roda de novo depois de uma falha. *Teste: Tarefa 3, `recupera uma vez só` e `falha não gera nova tentativa`.*
4. **Salvar Configurações na UI com módulos configurados:** a chave `modules` continua no `config.yaml`. *Teste: Tarefa 1, `updateConfig preserva modules`.*
5. **Página de módulo (origem `null`) tentando chamar uma rota do core ou de outro módulo:** recebe 403. Uma origem `null` também não pode derrubar a API com 500. *Teste: Tarefa 7, `Origin null fora do prefixo do módulo é 403` e `Origin null não gera 500`.*

5. `sdk !== SDK_VERSION`, `id` diferente da chave da config, ou `id` fora da regex: fica `falho`.
6. Se `scanSecrets(JSON.stringify(config))` achar algo: fica `falho` com "segredo na configuração do módulo <id>: use variável de ambiente ou o cofre do sistema". A mensagem não cita o valor.
7. Se `configSchema` existir, `validar` é chamado. Se der erro, fica `falho` com a mensagem.
8. Se `aba.pasta/index.html` não existir: fica `falho`.
9. `iniciar(ctx)` roda com timeout. Se lançar ou estourar o tempo, fica `falho`.

### Tarefa 3: Agendador

**Arquivos:**
- Criar: `packages/core/src/modules/{cron.ts,scheduler.ts}`
- Teste: `packages/core/test/modules-scheduler.test.ts`

**Interfaces:**
- Consome: `ModuleRegistry`, `modulesStateRoot` (Tarefa 2).
- Produz:
  - `parseCron(expr: string): Cron` lança `BrainError("invalid")` quando a expressão é inválida. `Cron.next(after: Date): Date` e `Cron.prev(before: Date): Date` usam hora local, e cada um dos 5 campos aceita `*`, número, lista, intervalo e passo.
  - `class Scheduler { constructor(reg: ModuleRegistry, root: string, o?: { agora?: () => Date; tickMs?: number }); start(): void; stop(): Promise<void>; runNow(id: string, tarefa: string, ocorrencia?: Date): Promise<ResultadoTarefa>; status(id: string): StatusTarefa[] }`.
  - `StatusTarefa = { tarefa: string; quando: string; proxima: string; ultimaOcorrencia?: string; inicio?: string; fim?: string; resultado?: "ok" | "erro" | "timeout"; erro?: string; suspensa: boolean; errosSeguidos: number }`.
  - `ResultadoTarefa = { resultado: "ok" | "erro" | "timeout"; erro?: string }`.
  - O estado fica em `<root>/_scheduler.json`, com a chave `"<id>/<tarefa>"`.

Regras (§7.8):
- O tick tem 30 s por padrão. Em cada tick, se `cron.prev(agora) > ultimaOcorrencia`, a ocorrência passa a ser `cron.prev(agora)`.
- **Atendida ao começar:** grava `ultimaOcorrencia` e `inicio` antes de chamar `rodar`.
- Na primeira subida sem registro, `ultimaOcorrencia = cron.prev(agora)` é gravado e **nada roda**.
- `recuperar: false`: na subida, se a ocorrência mais recente ficou para trás, ela é marcada como atendida sem rodar. Só as próximas ocorrências rodam.
- Salto de relógio: um tick que chega mais de `3 × tickMs` depois do anterior é tratado como suspensão, e a regra de subida é reaplicada.
- Uma tarefa nunca roda duas vezes ao mesmo tempo. Se o timeout (`timeoutS`, padrão 300) estourar, `abort()` é chamado no `sinal` e o resultado vira `timeout`.
- Depois de 5 erros seguidos, a tarefa fica `suspensa` até o `runNow` ou um reinício.
- Um erro também vai para `reg.recordError(id, "tarefa:<id>", e)`.

- [ ] **Passo 1: testes que falham** (relógio falso via `agora`, `tickMs: 10`):
  - `parseCron`: `"30 8 * * 1-5".next(sex 09:00)` → seg 08:30; `"*/15 * * * *"`; expressão com 4 campos lança.
  - `primeira subida não roda`: um contador fica em 0 depois de 3 ticks sem ocorrência nova.
  - `recupera uma vez só`: com registro de 3 dias atrás e `recuperar: true`, o contador vai a 1 depois de vários ticks, e a `ocorrencia` recebida é a mais recente que ficou para trás.
  - `recuperar false não recupera`: o contador fica em 0.
  - `falha não gera nova tentativa`: o `rodar` lança, o contador vai a 1, e depois de novos ticks sem ocorrência nova continua em 1, com `resultado: "erro"`.
  - `sem sobreposição`: um `rodar` lento seguido de um `runNow` → o segundo retorna erro "já em execução".
  - `timeout aborta`: com `timeoutS: 0.05` e um `rodar` que espera o `sinal`, o resultado é `timeout` e `sinal.aborted` é `true`.
  - `suspende após 5 erros`: com 5 ocorrências que falham, `suspensa` fica `true`, e o `runNow` volta a rodar e zera `errosSeguidos` se der certo.
  - `salto de relógio recupera`: o `agora` avança 2 dias entre um tick e outro, e a tarefa com `recuperar` roda uma vez.
- [ ] **Passo 2:** `pnpm vitest run packages/core/test/modules-scheduler.test.ts`. Esperado: FALHA.
- [ ] **Passo 3:** implementar `cron.ts`, sem dependência nova, e o `scheduler.ts`.
- [ ] **Passo 4:** rodar o mesmo comando. Esperado: PASSA.
